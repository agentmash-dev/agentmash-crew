# Bundle format and team install algorithm

Status: schema 1, agentmash-crew 1.1.0.

This document is for people who reimplement the team install outside this repository, such as the agentmash CLI (`npx agentmash team add ...`) and the agentmash.dev web installer. The reference implementation is `lib/team-plan.mjs` (pure functions) and `lib/install.mjs` (file system) behind `bin/agentmash-crew.mjs`.

The goal is that every installer, given the same bundle, the same repository state and the same sequence of operations, writes byte-identical files. All install knowledge lives in data (the bundle and its template), so the algorithm stays small: select files, substitute placeholders, merge one settings hook, write a manifest.

The words MUST, MUST NOT and SHOULD are used as in RFC 2119. "Implementation-defined" marks a choice this specification leaves open. Each one is followed by a quoted note on what the reference implementation does. Where that choice changes the bytes written, an installer that shares repositories with this one should make the same choice, or the two tools will keep rewriting each other's files.

## 1. Where the bundle comes from

`dist/bundle.json` is generated by `scripts/build-bundle.mjs` from the plugin sources in `plugin/` and the template in `templates/team-skill.md`, and committed. `npm run check` fails when the committed file is stale.

Fetch a released bundle by tag from jsDelivr:

```
https://cdn.jsdelivr.net/gh/IskakovDamir/agentmash-crew@v<version>/dist/bundle.json
```

The tag is `v` followed by `meta.version`, for example `v1.1.0`. Pin a tag: a branch URL can change under a cached installer.

### Plugin flavor and project flavor

The plugin in `plugin/` refers to its own files through `${CLAUDE_PLUGIN_ROOT}`. The bundle carries the project flavor, produced from the plugin sources by exactly these transforms:

1. In every agent file, the protocol pointer `${CLAUDE_PLUGIN_ROOT}/skills/crew-protocol/SKILL.md` becomes `.claude/skills/crew-protocol/SKILL.md`. There is exactly one occurrence per agent file, and the build fails if the count differs.
2. Everything else is copied byte for byte.

`${CLAUDE_PLUGIN_ROOT}` never appears in the bundle; the build fails if it does. Consumers do not transform content: they write `content` as it is.

## 2. Bundle schema

The bundle is one UTF-8 JSON document, serialized as `JSON.stringify(bundle, null, 2) + "\n"`. Keys appear in the order listed here.

```json
{
  "schema": 1,
  "meta": {
    "name": "agentmash-crew",
    "version": "1.1.0",
    "url": "https://github.com/IskakovDamir/agentmash-crew",
    "conductor": "mash-coordinator",
    "addCommand": "npx github:IskakovDamir/agentmash-crew team add <team> --agents <agent>",
    "hook": {
      "event": "PreToolUse",
      "matcher": "Bash",
      "command": "node \"$CLAUDE_PROJECT_DIR/.claude/agentmash-crew/crew-guard.mjs\"",
      "timeout": 5,
      "marker": ".claude/agentmash-crew/crew-guard.mjs"
    },
    "manifestPath": ".claude/agentmash-crew/teams.json"
  },
  "agents": [
    {
      "name": "mash-coordinator",
      "short": "mash",
      "title": "Mash",
      "role": "Crew coordinator",
      "group": "lead",
      "path": ".claude/agents/mash-coordinator.md",
      "sha256": "<64 hex chars>",
      "content": "---\nname: mash-coordinator\n..."
    }
  ],
  "shared": [
    { "path": ".claude/skills/crew-protocol/SKILL.md", "sha256": "…", "content": "…" },
    { "path": ".claude/skills/run-crew/SKILL.md", "sha256": "…", "content": "…" },
    { "path": ".claude/agentmash-crew/crew-guard.mjs", "sha256": "…", "content": "…" }
  ],
  "templates": {
    "teamSkill": {
      "pathPattern": ".claude/skills/team-{{team_slug}}/SKILL.md",
      "content": "…"
    }
  }
}
```

| Field | Type | Meaning |
|---|---|---|
| `schema` | integer | `1` for the format described here. |
| `meta.name` | string | `agentmash-crew`. Written to `teams.json` as `source.name`. |
| `meta.version` | string | The package version the bundle was built from (`package.json`). Written to `teams.json` as `source.version`. |
| `meta.url` | string | Repository URL. Written to `teams.json` as `source.url`. |
| `meta.conductor` | string | The agent that is a member of every team: `mash-coordinator`. |
| `meta.addCommand` | string | Command template shown to users for adding an agent to a team. `<team>` and `<agent>` are literal tokens (see `{{add_command}}` in section 6). |
| `meta.hook` | object | The one settings hook group an install adds (section 8). `marker` is the substring that identifies it. |
| `meta.manifestPath` | string | Where the manifest lives: `.claude/agentmash-crew/teams.json`. |
| `agents` | array | All 18 agents in canonical order (below). |
| `agents[].name` | string | Full agent name, also the agent file's frontmatter `name`. |
| `agents[].short` | string | The part of `name` before the first hyphen. |
| `agents[].title` | string | `short` capitalized: `Mash`. |
| `agents[].role` | string | One-line role, at most 60 characters: the text after ` · ` in the agent's H1 (`# Mash · Crew coordinator`), else a short role derived from the first sentence of the description. |
| `agents[].group` | string | `lead`, `build`, `quality`, `ops` or `docs`. |
| `agents[].path` | string | Install path: `.claude/agents/<name>.md`. |
| `agents[].sha256`, `shared[].sha256` | string | Hex SHA-256 of the UTF-8 bytes of `content`. |
| `agents[].content`, `shared[].content` | string | The exact file content to write. |
| `shared` | array | Files every project install needs once, in the order shown. |
| `templates.teamSkill.pathPattern` | string | Path of a team's skill; `{{team_slug}}` is the only placeholder in it. |
| `templates.teamSkill.content` | string | The team skill template (section 6). |

### Canonical order and groups

Everywhere members are listed (the bundle, `teams.json`, rendered placeholders), agents appear in this order:

| # | Name | Short | Group |
|---|---|---|---|
| 1 | mash-coordinator | mash | lead |
| 2 | tally-planner | tally | lead |
| 3 | scout-explorer | scout | lead |
| 4 | flex-frontend | flex | build |
| 5 | pipe-backend | pipe | build |
| 6 | swipe-mobile | swipe | build |
| 7 | index-database | index | build |
| 8 | patch-integrations | patch | build |
| 9 | batch-ml | batch | build |
| 10 | spell-prompts | spell | build |
| 11 | lingo-i18n | lingo | build |
| 12 | probe-qa | probe | quality |
| 13 | gavel-reviewer | gavel | quality |
| 14 | snag-debugger | snag | quality |
| 15 | prune-refactor | prune | quality |
| 16 | bump-dependencies | bump | ops |
| 17 | rail-cicd | rail | ops |
| 18 | quill-docs | quill | docs |

The canonical order is the order of `bundle.agents`. An implementation SHOULD take it from the bundle rather than hard-code it.

## 3. Verification

Before writing anything, an installer MUST:

1. Verify every `sha256` in `agents` and `shared`: compute SHA-256 over the UTF-8 encoding of `content` and compare the hex digest.
2. Reject every path that:
   - is absolute, contains `..` or a backslash, or does not start with `.claude/`;
   - contains a character other than the ASCII letters, digits, `.`, `_`, `-` and `/`, or an empty or `.` segment;
   - is `.claude/settings.json` (that file is merged, never written from the bundle) or lies under `.claude/agentmash/` (section 4). These two comparisons ignore ASCII letter case, because on a case-insensitive file system (the macOS and Windows defaults) `.claude/Settings.json` is the settings file.

   This applies to `agents[].path`, `shared[].path`, `meta.manifestPath`, the team skill path after rendering, and every key of the manifest's `files` map (section 7).

If either check fails, the installer MUST NOT write any file from that bundle.

Restricting paths to ASCII means letter case is the only way two different strings can name the same file, which is what the manifest checks in section 7 rely on.

How a consumer treats a `schema` value other than `1`, and which further checks it runs, is implementation-defined.

> Reference implementation (`verifyBundle` and `pathProblem` in `lib/team-plan.mjs`): rejects any `schema` other than `1`; requires every `meta` string, a positive integer `meta.hook.timeout`, `<team>` in `meta.addCommand` and the marker inside `meta.hook.command`; requires unique agent names and shorts, `short` equal to the name before the first `-`, the conductor as the first agent, and roles of at most 60 code points without `|` or line breaks; rejects a path used twice. The template may use only the seven placeholders of section 6, and `pathPattern` only `{{team_slug}}`.

## 4. Files an install writes

All paths are relative to the repository root.

| Path | Source | Written when |
|---|---|---|
| `.claude/agents/<name>.md` | `agents[].content` (project flavor) | the agent is a member of at least one team |
| `.claude/skills/crew-protocol/SKILL.md` | `shared[]` | any team exists |
| `.claude/skills/run-crew/SKILL.md` | `shared[]` | any team exists |
| `.claude/agentmash-crew/crew-guard.mjs` | `shared[]` | any team exists |
| `.claude/skills/team-<slug>/SKILL.md` | `templates.teamSkill`, rendered | per team |
| `.claude/agentmash-crew/teams.json` | the manifest (section 7) | any team exists |
| `.claude/settings.json` | merged: one `PreToolUse` hook group (section 8) | any team exists |

Content is written exactly as given: UTF-8, no byte order mark, no line-ending conversion. Anything else would break the byte-identity requirement and the hashes recorded in the manifest.

`.claude/agentmash/` belongs to the agentmash CLI, whose `uninstall` deletes it. A crew installer MUST NOT write, move or delete anything there.

The repository is untrusted input: a clone or a pull request can commit symbolic links. An installer MUST NOT read, write or delete a path when the file itself or any directory on the way to it, below the repository root, is a symbolic link, and MUST NOT write or delete a path that exists but is not a regular file. Otherwise a committed link such as `.claude/agents -> /somewhere/else` would make the install write outside the repository.

## 5. Team names and slugs

### Name

The display name is what the user typed, for example `Команда 123`, after trimming leading and trailing whitespace. It MUST be 1 to 60 characters long and MUST NOT contain control characters or newlines. It MUST NOT contain `"`, `\`, `$`, `` ` `` or `!`: the team skill puts the name inside a double-quoted YAML string, and the add command it shows puts the name inside double quotes on a shell command line (section 6), where `$`, `` ` `` and `!` still expand. The same rule applies to names read from an existing manifest (section 7).

How "characters" are counted for the 60 limit is implementation-defined.

> Reference implementation: counts Unicode code points, and treats C0 and C1 control characters, U+007F, U+2028 and U+2029 as forbidden.

### Slug

The slug is the `--slug` value when one is given. Otherwise it is derived from the name:

1. Lowercase the name.
2. Replace each Russian or Kazakh Cyrillic letter by its Latin form from the table below. A letter that maps to an empty string is removed.
3. Replace every run of characters outside `[a-z0-9]` with a single `-`.
4. Trim `-` from both ends.
5. Cut to 40 characters, then trim trailing `-` again.

The result MUST match `^[a-z0-9][a-z0-9-]{0,39}$`. If it is empty (for example a name written only in a script the table does not cover), the installer MUST fail with an error that asks for `--slug`. A slug is derived only when one is needed: `add` with the exact name of an existing team uses that team's slug (section 9), so a team created as `日本` with `--slug nihon` is extended by its name alone.

Transliteration table (lowercase; uppercase letters are lowercased in step 1):

| Cyrillic | Latin | Cyrillic | Latin | Cyrillic | Latin |
|---|---|---|---|---|---|
| а | a | р | r | ә | a |
| б | b | с | s | ғ | g |
| в | v | т | t | қ | q |
| г | g | у | u | ң | n |
| д | d | ф | f | ө | o |
| е | e | х | h | ұ | u |
| ё | e | ц | ts | ү | u |
| ж | zh | ч | ch | һ | h |
| з | z | ш | sh | і | i |
| и | i | щ | shch | | |
| й | i | ъ | (removed) | | |
| к | k | ы | y | | |
| л | l | ь | (removed) | | |
| м | m | э | e | | |
| н | n | ю | yu | | |
| о | o | я | ya | | |
| п | p | | | | |

The first two columns are the 33 letters of the Russian alphabet; the third column is the 9 additional letters of the Kazakh alphabet.

Examples:

| Name | Slug |
|---|---|
| `Команда 123` | `komanda-123` |
| `Қазақ тобы` | `qazaq-toby` |
| `Щука & Юла` | `shchuka-yula` |
| `Ёлка-2026` | `elka-2026` |
| `Backend Squad (EU)` | `backend-squad-eu` |
| `Алматы: платежи и подписки для мобильного приложения` | `almaty-platezhi-i-podpiski-dlya-mobilnog` (cut at 40) |
| `日本` | empty: error, `--slug` required for a new team |

Whether the name is Unicode-normalized before step 1 (a decomposed `й` is `и` followed by U+0306), and whether a `--slug` value is lowercased before it is checked, are implementation-defined.

> Reference implementation (`slugify` in `lib/team-plan.mjs`): `String.prototype.toLowerCase`, then the table, per code point; no normalization, so `йога` typed with a decomposed `й` becomes `i-oga` instead of `ioga`. A `--slug` value is used as given and must already match the pattern.

### Uniqueness

Two teams in one repository MUST NOT share a slug. `add` with a name or a slug that matches an existing team extends that team instead of creating a new one (section 9).

The team's skill name is `team-<slug>`, at most 45 characters, which is a valid Claude Code skill name.

## 6. Rendering the team skill

The team skill is `templates.teamSkill.content` with placeholders replaced, written to `pathPattern` with `{{team_slug}}` replaced by the slug.

The template uses only these placeholders. Each is substituted literally: no escaping, no conditionals, no other template syntax.

| Placeholder | Value | Example for `Команда 123` with pipe, flex, probe |
|---|---|---|
| `{{team_name}}` | The display name | `Команда 123` |
| `{{team_slug}}` | The slug | `komanda-123` |
| `{{skill_name}}` | `team-` + slug | `team-komanda-123` |
| `{{members_inline}}` | Member full names in canonical order, joined with `, ` | `mash-coordinator, flex-frontend, pipe-backend, probe-qa` |
| `{{roster_table}}` | A markdown table: header and separator rows, then one row per member in canonical order with the agent's `title`, its `name` in backticks and its `role` | see section 11 |
| `{{missing_inline}}` | Crew agents not in the team, same format as `{{members_inline}}`, or `none` when the team has all 18 | `tally-planner, scout-explorer, swipe-mobile, …` |
| `{{add_command}}` | `meta.addCommand` with `<team>` replaced by the display name in double quotes; `<agent>` stays literal | `npx github:IskakovDamir/agentmash-crew team add "Команда 123" --agents <agent>` |

The template's frontmatter puts the description in double quotes, and `{{add_command}}` puts the name in double quotes on a shell command line that users copy. That is why names containing `"`, `\`, `$`, `` ` `` or `!` are rejected (section 5): with literal substitution they would break the YAML, or expand in bash, zsh or PowerShell so that the command addresses another team.

Rendering is deterministic: the same bundle and the same team produce byte-identical output.

The exact header of `{{roster_table}}`, and whether substituted values are scanned again for placeholders, are implementation-defined. Both change the output bytes, so an implementation that wants byte-identical installs with this repository SHOULD match the reference:

> Reference implementation (`renderTeamSkill` in `lib/team-plan.mjs`): the table is the lines `| Agent | Name | Role |` and `| --- | --- | --- |` followed by one `` | <title> | `<name>` | <role> | `` line per member, joined with `\n`, with no trailing newline. All placeholders are replaced in a single pass over the template (one regular expression, `\{\{([a-z_]+)\}\}`), so a team literally named `{{team_slug}}` stays literal. `<team>` is replaced at every occurrence in `meta.addCommand`.

## 7. The manifest: teams.json

`.claude/agentmash-crew/teams.json` records what the installer owns in the repository.

```json
{
  "schema": 1,
  "source": { "name": "agentmash-crew", "version": "1.1.0", "url": "https://github.com/IskakovDamir/agentmash-crew" },
  "createdSettings": false,
  "teams": [
    { "slug": "komanda-123", "name": "Команда 123", "members": ["mash-coordinator", "pipe-backend"] }
  ],
  "files": {
    ".claude/agents/mash-coordinator.md": "<sha256 hex of the bytes written>"
  }
}
```

| Field | Meaning |
|---|---|
| `schema` | `1`. |
| `source` | `name`, `version` and `url` from the bundle's `meta` that produced the current files. |
| `createdSettings` | `true` when the installer created `.claude/settings.json` (it did not exist before the first team was added). Governs whether the file may be deleted when the last team is removed (section 8). |
| `teams` | One entry per team: `slug`, `name` (display name), `members` (full names, canonical order, always including `meta.conductor`). |
| `files` | Every file the installer wrote, except `settings.json` and `teams.json` itself, mapped to the hex SHA-256 of the bytes written. |

Serialization:

- Keys in the order shown, `JSON.stringify(manifest, null, 2) + "\n"`.
- `teams` sorted by `slug`; `members` in canonical order; `files` keys sorted. Slugs and paths are ASCII, so plain code-point order is byte order.
- No timestamps, no machine- or user-specific values, so two installs of the same teams are byte-identical.

### The manifest is untrusted

`teams.json` is committed, so anyone who can open a pull request can edit it, and it decides which files an operation deletes (section 9). Before acting on a manifest, an installer MUST check:

1. Every team's `name` and `slug` pass section 5.
2. Every `files` key passes the path checks of section 3.
3. No `files` key is the manifest path, and no `files` key equals, ignoring ASCII letter case but not exactly, the manifest path, another key, or a path the bundle can produce: an `agents[].path`, a `shared[].path`, or `pathPattern` rendered with any slug that matches section 5. On a case-insensitive file system `.claude/Agents/pipe-backend.md` is `.claude/agents/pipe-backend.md`, so such a key could otherwise delete a file the plan keeps.

An installer MUST NOT read, write or delete anything through a key that fails these checks. The manifest never supplies content: every byte an installer writes comes from the bundle, and the manifest only decides which files count as the installer's, and so which may be deleted.

How an installer treats a manifest it cannot trust (invalid JSON, another schema, duplicate slugs, a failed check above), whether it refuses the whole file or skips the bad entries, is implementation-defined.

> Reference implementation (`parseManifest` in `lib/team-plan.mjs`): refuses to run and asks the user to fix the file.

## 8. Settings merge and unmerge

An install adds one hook group to `hooks.PreToolUse` in `.claude/settings.json`, built from `meta.hook`:

```json
{ "matcher": "Bash", "hooks": [ { "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR/.claude/agentmash-crew/crew-guard.mjs\"", "timeout": 5 } ] }
```

Detection: the group is already present when the JSON serialization of any existing `hooks.PreToolUse` group contains the marker `.claude/agentmash-crew/crew-guard.mjs` as a substring. A present group is never added twice and never rewritten.

### Merge (whenever at least one team exists)

1. `settings.json` does not exist: create `{ "hooks": { "PreToolUse": [group] } }` and set `createdSettings` to `true` in the manifest.
2. `settings.json` exists but is not a JSON object, or is JSONC with comments: abort before writing anything, anywhere, with a message that names the file and the problem.
3. Otherwise add the group when the marker is absent, creating `hooks` and `hooks.PreToolUse` if needed. Preserve every other key and every other group.
4. Serialize as `JSON.stringify(settings, null, 2) + "\n"`. Do not rewrite the file when nothing changed, so a repository whose settings already carry the group sees no diff and keeps its own formatting.

Where the new group goes in an existing `PreToolUse` array, and what happens when `hooks` or `hooks.PreToolUse` exists with the wrong type, are implementation-defined.

> Reference implementation (`mergeSettings` in `lib/team-plan.mjs`): appends the group at the end of `PreToolUse`; aborts, before writing anything, when `hooks` is not an object or `hooks.PreToolUse` is not an array. `createdSettings` stays `true` in later manifests once it was set.

### Unmerge (when the last team is removed)

Users add their own hooks to the group the installer created (it matches `Bash`, so a second Bash hook naturally goes into its `hooks` array). The unmerge therefore removes the installer's hook entry, not the whole group:

1. In every `hooks.PreToolUse` group whose `hooks` value is an array, remove each entry whose JSON serialization contains the marker. Keep the remaining entries in order.
2. Delete a group that lost an entry in step 1 when its `hooks` array is now empty and it has no keys other than `matcher` and `hooks`. A group that still holds entries or other keys stays, with its keys in their original order and `hooks` set to the remaining entries. Groups that lost nothing are not touched.
3. Drop `PreToolUse` if it became empty, then drop `hooks` if it became empty.
4. Delete `settings.json` only if it is now exactly `{}` and the manifest says `"createdSettings": true`. Otherwise write it back (same serialization) when step 1 removed anything, or leave it untouched when nothing changed.

What happens when `settings.json` cannot be parsed during a removal, and whether a kept group is reported, are implementation-defined.

> Reference implementation (`unmergeSettings`): the same parse rules as the merge apply, so the removal stops before anything is written or deleted. When a group stays because it holds something else, the removal prints a warning.

## 9. Operations

The reference CLI exposes three operations: `team add <name> --agents <list> [--slug <slug>]`, `team remove <name-or-slug> [--agents <list>]` and `team update`, each with `--dry-run` (plan only) and `--force` (see below).

This specification fixes these rules:

- Members are given as short or full names, case-insensitive, or `all`. `meta.conductor` is a member of every team and cannot be removed from one.
- `add` with the name or the slug of an existing team extends that team.
- After any operation, the files on disk are the ones section 4 requires for the resulting teams, the manifest describes them (section 7), and settings are merged or unmerged (section 8).
- Nothing is written or deleted when the bundle fails verification (section 3), a path of the plan runs through a symbolic link (section 4), the manifest fails its checks (section 7) or `settings.json` cannot be merged (section 8).

Everything else in this section (how an operation finds its team, what it refuses, how it treats files it did not write or that the user changed) is implementation-defined. It is described as the reference implementation behaves (`planChange` in `lib/team-plan.mjs`, `apply` in `lib/install.mjs`), because an installer that works on the same repositories as this one needs the same decisions to produce the same files.

### Desired state

For the resulting set of teams the installer wants the three shared files, `.claude/agents/<name>.md` for the union of all teams' members, and one rendered skill per team. With no teams left it wants nothing. One agent file serves every team that includes the agent.

### add

1. Validate the name (section 5).
2. Find the target team. Without `--slug`: a team with exactly this display name is the target, and no slug is derived; otherwise derive the slug (section 5, which fails when it comes out empty) and look for a team with that slug. With `--slug`: validate it; if the name matches a team whose slug differs from `--slug`, fail; otherwise the target is the team with this name, else the team with this slug. If only the slug matches (a different name that produces the same slug), extend that team, keep its original name, and warn.
3. A new team's members are the resolved list plus the conductor, in canonical order. A new team needs at least one agent besides the conductor.
4. An existing team gains the new members, in canonical order. Its skill is re-rendered, because `{{members_inline}}`, `{{roster_table}}` and `{{missing_inline}}` changed.

### remove

- The team is found by exact display name, exact slug, or the slug the given text would produce, so `"Команда 123"` and `komanda-123` both work.
- Without an agent list, the team is removed: its skill is deleted, and so is every agent file no remaining team needs. Removing the last team deletes every tracked file and the manifest, and unmerges settings (section 8).
- With an agent list, those agents leave the team. Naming the conductor is an error, and so is leaving the conductor alone in the team (remove the team instead). Naming an agent that is not a member only warns.

### update

Re-plans the existing teams against the current bundle: changed files are rewritten, files no longer needed are deleted, and the manifest records the new `source` and hashes. Members the new bundle does not know are dropped from their teams with a warning. Without a manifest there is nothing to update, which is an error.

`add` and `remove` also bring every installed file to the running bundle's version, which can be older than `source.version` in the manifest. The reference implementation warns when `source.version` differs from `meta.version` on `add` and `remove`, and writes the files anyway.

### Foreign and user-modified files

The manifest's `files` map is how the installer tells its own files from the user's. For each file in the desired state it compares the SHA-256 on disk with the desired content's hash and with the hash it recorded last time, in this order:

| Case | Action | Hash recorded in the new manifest |
|---|---|---|
| On disk equals the desired content | unchanged (a matching file the manifest did not list is adopted) | desired |
| Missing | created | desired |
| On disk equals the recorded hash | updated: it was ours and nobody changed it | desired |
| Differs, and `--force` was given | overwritten | desired |
| Differs, and the manifest does not list it | **foreign**: the whole operation fails before anything is written, listing every such file | none |
| Differs from both desired and recorded | **kept**: changed by the user, left as it is; a warning when the desired content differs from the recorded hash (the user's copy misses a newer version) | the old recorded hash, so it still counts as changed next time |

For a tracked file that the desired state no longer contains:

| Case | Action |
|---|---|
| Already missing | dropped from the manifest |
| On disk equals the recorded hash | deleted; parent directories left empty are removed, up to but not including `.claude/` |
| Changed by the user | **left** on disk with a warning, and dropped from the manifest |

The symbolic link rule of section 4 is checked for every path of the plan before the first write. The reference implementation writes files first, then `settings.json`, then the manifest, so an interrupted run leaves a manifest that still describes the previous state. It writes each file to a temporary file next to it (`<name>.agentmash-tmp-<pid>`), flushes it and renames it over the target, so a write that fails, for example on a full disk, leaves the old file whole instead of a truncated one that the next run would take for a local edit.

## 10. Determinism requirements

Two conforming installers, given the same bundle, the same starting repository and the same operations, MUST produce byte-identical files. In particular:

- Agent and shared files: `content` written exactly, UTF-8, no BOM, no line-ending conversion.
- Team skill: literal placeholder substitution; members and missing agents in canonical order; `none` for an empty missing list.
- `teams.json`: key order as in section 7, teams sorted by slug, members in canonical order, `files` keys sorted, no timestamps, two-space JSON plus a trailing newline.
- `settings.json`: two-space JSON plus a trailing newline, and no write at all when the content would not change.
- The bundle itself: agents in canonical order, keys in the order of section 2, two-space JSON plus a trailing newline.
